# AirRemote frontend

The V2 app for Android, iOS and web: React Native on Expo SDK 58, with
development builds (not Expo Go). It talks to the V2 API in `backend/` and
validates every response with `@airremote/contracts`. How the code is
organised is in `frontend/ARCHITECTURE.md`.

## Prerequisites

- Node 24
- pnpm 10 (`corepack enable` or `npm i -g pnpm@10`)
- The API running on your machine: `pnpm dev` at the repository root (see
  `backend/README.md`), and the mock device for the device screens (see
  "The whole app on your machine")
- For Android: Android Studio with the Android SDK and an emulator (or a
  phone with USB debugging), and JDK 17. Java 25 is too new for the Android
  build; point `JAVA_HOME` at a JDK 17.
- For iOS: a Mac with Xcode, or an EAS build (no EAS project is set up yet).

`android/` and `ios/` are generated by `expo prebuild` (or the first
`android`/`ios` run) and git-ignored.

## Environment

The app reads two variables, validated in `src/config/env`:

| Variable              | What it is                                      |
| --------------------- | ----------------------------------------------- |
| `EXPO_PUBLIC_APP_ENV` | `development` or `production`                   |
| `EXPO_PUBLIC_API_URL` | The API's base URL (`http` or `https`, no path) |

Their values are committed, since none is secret: `frontend/.env.development`
(API at `http://localhost:3000`) and `frontend/.env.production`. A wrong or
missing value stops the app at startup with `Invalid environment: ...`.

`EXPO_PUBLIC_APP_ENV` also picks the app id: development builds are
`com.airremote.app.dev` ("AirRemote Dev"), so they install next to a
production build (`com.airremote.app`).

**Local overrides** go in `frontend/.env.development.local`, which is
git-ignored. In development the committed `.env.development` wins over
variables set in the shell, so `EXPO_PUBLIC_API_URL=... pnpm web` has no
effect; use the file:

```bash
# Android emulator: the host machine is 10.0.2.2
EXPO_PUBLIC_API_URL=http://10.0.2.2:3000
# A phone on the same Wi-Fi: your computer's LAN address
EXPO_PUBLIC_API_URL=http://192.168.1.10:3000
```

Restart the dev server after changing an env file. The API listens on all
interfaces by default, so a phone can reach it at the LAN address.

A phone or emulator makes plain native requests, so it needs no CORS. The
web app runs on another origin (`http://localhost:8081`), so the API must
list it in `CORS_ORIGINS` (`.env.example` already does, and `pnpm dev` adds it
when it is missing); restart `pnpm dev` after changing it.

## Run it

Run these from `frontend/`, or from the root with
`pnpm --filter @airremote/frontend <script>`.

**Web:** `pnpm dev` at the repository root runs the API and the web app
together; open http://localhost:8081. `pnpm web` here starts only the app,
for an API that is already running (`pnpm dev --api-only`).

**Android:** `pnpm android` builds a development build, installs it on the
running emulator or the connected phone, and starts the dev server. Until
native code or native dependencies change, `pnpm start` is enough: the
installed build connects to it (`pnpm dev` at the root already runs it).

**iOS:** `pnpm ios` on a Mac, the same way. On Linux, iOS builds need EAS.

| Script                  | What it does                                                   |
| ----------------------- | -------------------------------------------------------------- |
| `pnpm start`            | Starts the dev server for an installed development build       |
| `pnpm web`              | Starts the dev server and serves the web app on port 8081      |
| `pnpm android`          | Builds and installs the Android development build, then starts |
| `pnpm ios`              | Builds and installs the iOS development build (Mac only)       |
| `pnpm prebuild`         | Generates `android/` and `ios/` from `app.config.ts`           |
| `pnpm typecheck`        | Type-checks the app                                            |
| `pnpm test`             | Runs the Jest tests                                            |
| `pnpm create-new`       | Scaffolds new files (below)                                    |
| `pnpm exec expo-doctor` | Checks the Expo setup and dependency versions                  |

From the root, `pnpm lint`, `pnpm typecheck` and `pnpm format` cover the
frontend too, and `pnpm test:frontend` runs its tests. The root `pnpm test`
and `pnpm test:unit` run them after Vitest.

## Scaffolding

```bash
pnpm create-new <kind> [name] [--module <m>] [--persisted]
```

Without a kind and name it asks. It never overwrites a file, and prints
what to add by hand (a navigator registration, a param list entry, a
`resources.ts` line) and a Prettier command for the new files.

| Kind        | Creates                                                                    |
| ----------- | -------------------------------------------------------------------------- |
| `component` | `src/components/<name>/`                                                   |
| `screen`    | `src/screens/<name>-screen/` and its title key                             |
| `hook`      | `src/hooks/use-<name>/`                                                    |
| `store`     | `src/stores/<name>/`; `--persisted` adds a `STORE_PERSIST_KEY` entry       |
| `helper`    | `src/helpers/<name>/` with a constants file                                |
| `domain`    | `src/api/<name>/` and `src/queries/<name>/` (API, keys, mutations)         |
| `module`    | `src/modules/<name>/` with its folders, navigator, i18n and a first screen |

Each comes with its test and `index.ts`. `--module <m>` puts a component,
screen, hook, store or helper inside `src/modules/<m>/`. A domain is named like
its backend resource (`domain devices` calls `/devices`) and starts with
placeholder schemas and a list, get and create call: replace the schemas with
the contract's and keep only the calls the backend has. A module's first
screen is `<name>-list-screen/`, route `<Name>List`, inside the stack that
the root route `<Name>` mounts (`module devices` makes `DevicesList` inside
`Devices`): a nested route named like its parent makes React Navigation warn
and `navigate` ambiguous. Rename it if the module's first screen is not a
list. After creating a module, restart your editor's ESLint server so the
module's import rules apply.

## The whole app on your machine

To use every screen (sign up, devices, remotes, learning and pressing
buttons) you need the API, its device listener and a device. The mock
device stands in for a board (`tools/device-sim/README.md`):

1. Once: `cp .env.example .env` at the repository root (it already has
   `CORS_ORIGINS=http://localhost:8081` for the web app), then create the
   device listener's certificates and one for the mock device. The first
   command prints the three `DEVICE_TLS_*` lines to put in `.env`:

   ```bash
   scripts/dev-certs.sh
   scripts/dev-certs.sh device AA:BB:CC:DD:EE:01
   ```

2. `pnpm dev` at the root: Postgres, migrations, then the API on
   http://localhost:3000, the device listener on https://localhost:8443 and
   the web app on http://localhost:8081.
3. In another terminal, `pnpm device-sim --mac AA:BB:CC:DD:EE:01`, then
   type `/enroll`: it prints a pairing code (and a QR code).
4. Open http://localhost:8081, sign up, log in, then Devices → ⊕ → Next →
   "Enter manually" with the MAC and the code (or scan the QR code on a phone). The mock connects
   within 5 s; the tile says Connected at the next refresh (30 s, or when
   you come back to the tab).
5. Remotes → ⊕ adds a remote on the device; open it and ⊕ to learn a
   button: when the app is listening, type `/press` in the mock. Press the
   button's circle to send it. `/disconnect` and `/connect` in the mock
   take it offline and back; `/send-fails on` makes presses fail.

To point the app at another API (a second one on another port, or the
computer from a phone), put `EXPO_PUBLIC_API_URL` in
`frontend/.env.development.local` and restart the dev server (see Local
overrides).

## Manual checks on a device

These checks haven't been run on a device yet (there is no Android SDK or
Mac where the app was built). Before relying on Android or iOS, run them on
a development build against `pnpm dev` and the mock device, set up as in
"The whole app on your machine", with `EXPO_PUBLIC_API_URL` pointing at
the computer:

1. Install the development build (`pnpm android` / `pnpm ios`); the app
   starts on Login, in V1's look: Poppins in the empty states, the blue
   gradient on the sign-in button.
2. Sign up, then sign in: the app opens on Remotes. The top bar and every
   screen's content sit below the status bar and the notch, not under
   them, on Login and Sign up too; the tab bar clears the home indicator.
3. Send the app to the background and bring it back: still signed in, on
   the same tab.
4. Turn on airplane mode, then kill and reopen the app: "Couldn't connect"
   with Retry. Turn airplane mode off and press Retry: Remotes.
5. Wait more than 10 minutes (the access token's lifetime), then open
   Devices. The refresh is invisible: no sign-out, no Error dialog. To
   check it sooner, shorten the token's lifetime locally: set
   `ACCESS_TOKEN_TTL_SECONDS` in `backend/src/features/auth/auth.helpers.ts`
   to e.g. `30`, restart `pnpm dev`, sign in again, and revert it
   afterwards (never commit it).
6. Kill the app and open it again: still signed in. This is the refresh
   cookie surviving a restart, which is unverified on native.
7. Devices → ⊕ → Next: the app asks for the camera (the prompt says it
   scans the pairing code). Allow it, then point it at the mock device's
   QR code (`/enroll`): the dialog moves to the name with the board and
   code filled in. A QR code that isn't a pairing link shows "That QR code
   isn't an AirRemote pairing code." and keeps scanning. Deny the camera
   and reopen: "Camera access is turned off…", with "Enter manually" still
   there.
8. Pairing links, with `airremote://pair?mac=<MAC>&code=<CODE>` opened by
   `adb shell am start -a android.intent.action.VIEW -d "<link>"` or
   `xcrun simctl openurl booted "<link>"`:
   - cold start (the app closed, signed in): Devices opens with the dialog
     at the name, filled in;
   - warm start (the app open on another tab): the same;
   - signed out: Login first; after signing in the app opens on Devices
     with the dialog filled in.
9. Edit mode (the pencil) on Devices, Remotes and a remote's buttons: the
   tiles wobble and show the × badge half over their corner. Tap the
   badge's outer half, outside the tile, on Android: it must still open
   the confirmation (Android may not deliver touches outside a view's
   bounds).
10. Learn a button (`/press` in the mock while the bar sweeps), then press
    it: the spinner, then the green tick drawn with its pop. The progress
    bar, the tick and the pop are Reanimated and react-native-svg
    animations that were only checked on web.
11. Sign out from the account menu: back on Login, and reopening the app
    stays on Login.

## Common failures

- **"Couldn't connect" at launch, or every request fails:** the API is not
  running, or the device can't reach `EXPO_PUBLIC_API_URL` (`localhost` on
  an emulator or phone is the device itself; see Local overrides).
- **Web: requests blocked by CORS, or signed out on reload:** the root
  `.env` lacks `CORS_ORIGINS=http://localhost:8081`, or the API was not
  restarted after adding it.
- **An env change has no effect:** shell variables lose to
  `.env.development`; put it in `.env.development.local` and restart the
  dev server.
- **The Android build fails on Java or Gradle versions:** use JDK 17
  (`java -version`, `JAVA_HOME`).
- **ESLint misses a new module's rules in the editor:** restart the ESLint
  server; the CLI (`pnpm lint`) always reads the current modules.
- **"Using src/app as the root directory for Expo Router"** in the dev
  server's log: harmless; the app does not use Expo Router.
