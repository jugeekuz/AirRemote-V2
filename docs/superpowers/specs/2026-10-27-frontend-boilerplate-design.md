# Frontend boilerplate and skills — design

Date: 2026-10-27 · Branch: `rewrite/frontend-boilerplate`

## Intent

The V2 frontend is a React Native app (see the owner's choice of React Native
over React web). The owner brought `REACT_NATIVE_BLUEPRINT.md` from another
project: an architecture (layers, state ownership, naming, API layer, tests)
written for an agent scaffolding a new app. This change ports that
architecture into `frontend/`, adapted to this repository, and writes the
Claude Code skills future agents follow to build on it.

The next change (not this one) builds Login, Devices, Remotes and Buttons to
look identical to V1, with anything the V2 backend does not have yet visibly
not working. This change must leave everything that change needs in place:
the UI kit, the auth plumbing, navigation, i18n, tests and the recipes.

V1's frontend (`legacy/frontend`, Vite + React + NextUI + Tailwind) kept server
data in components and contexts and had no tests. That is what this
architecture exists to prevent.

## Goals

- `frontend/` is an Expo app (`@airremote/frontend`) in the pnpm workspace,
  for Android, iOS and web, that starts on all three in development.
- The blueprint's architecture (§2: layers, import rules, state ownership,
  naming) holds and ESLint enforces the import rules.
- One HTTP client that attaches the access token, refreshes it on a 401 and
  retries, and validates responses against `@airremote/contracts`.
- Server state in TanStack Query, client state in Zustand, as the blueprint
  describes.
- A vendored copy of HeroUI Native behind `@ui`, styled with Tailwind classes
  through Uniwind, so V1's NextUI/Tailwind screens can be ported closely.
- Jest tests for every layer the blueprint says to test, run by the root
  `pnpm test`.
- A scaffolding generator (`create-new`) for every kind of file.
- Claude Code skills in `.claude/skills/` and a frontend section in the root
  `CLAUDE.md`, so an agent can add a feature without reading the blueprint.

## Non-goals

- **No product screens.** Login, Devices, Remotes and Buttons, V1's look,
  fonts, icons and colours are the next change. No `devices`, `remotes` or
  `buttons` API/queries either.
- No backend changes other than CORS (below).
- No CI, no EAS project set up or store submission, no push notifications,
  no analytics or crash reporting (only the `logError` hook point).
- No authorization helpers / `use-authorization`: V2 has no roles or
  permissions. The recipe for adding them can come when they exist.
- No Electron.
- `legacy/frontend` stays: it is removed when V2's frontend replaces it.

## Anti-goals

- Server data copied into a Zustand store or a context.
- App code importing HeroUI, `axios`, MMKV or a platform library directly
  instead of through `@ui`, `@api/http-client` or an adapter.
- Signing the user out when the access token expires. It lasts 10 minutes;
  an expiry must be invisible to the user.
- Copying V1's code or structure, or importing from `legacy/` (root
  `CLAUDE.md`).
- Any BOX names, URLs or code from the blueprint's origin project.

## Decided by the owner

- **React Native on Expo, with development builds** (not Expo Go). `android/`
  and `ios/` are generated by `expo prebuild` and not committed. iOS is built
  on EAS or a Mac; the owner develops on Linux.
- **Platforms:** Android, iOS and web.
- **App id:** `com.airremote.app` (Android package and iOS bundle id).
- **UI kit:** HeroUI Native (NextUI's successor; V1 used NextUI), **vendored**:
  its source is copied into the repo and owned by us, not installed from npm.
- **pnpm workspace**, not yarn. The app lives in `frontend/` and uses
  `@airremote/contracts`.
- **The API layer follows the V2 backend:** plain JSON bodies (no
  `{ payload }` envelope), errors as `{ error: { code, message, details? } }`
  (`errorResponseSchema`), responses validated with the contract schemas.
- **Token refresh on 401, like V1:** V1 kept the token in memory, called
  refresh at startup (the refresh token is an httpOnly cookie), and on a 401
  refreshed and retried the request once, signing out only if the refresh
  failed. V2 does the same (details below).
- **CORS in the backend now**, so the web app can sign in from another
  origin (see "Backend: CORS").
- **No commitlint.** The repo's commit style is not conventional commits.
- **Skills, not `.github/instructions`:** the blueprint's Phase 14 agent docs
  become Claude Code skills plus a frontend section in `CLAUDE.md`.
- **The blueprint's stack otherwise stands:** TanStack Query v5, Zustand v5,
  axios, React Navigation v7 (dynamic API, typed param lists), react-hook-form,
  i18next + react-i18next with typed keys, MMKV v4 for persisted client state,
  Jest + @testing-library/react-native, latest stable versions pinned exactly.

## Design

### Workspace integration

- `pnpm-workspace.yaml` gains `frontend`. Expo SDK 58 supports pnpm's
  isolated `node_modules` and detects the monorepo in Metro; nothing is
  hoisted for the backend's sake.
- Root scripts keep working and now cover the frontend:
  - `pnpm lint` (`eslint .`): the root `eslint.config.js` gains the frontend
    blocks (React, hooks, TanStack Query, layer boundaries). The repo is on
    ESLint 10, which `@react-native/eslint-config` and `eslint-config-expo`
    may not support: use the individual plugins (`eslint-plugin-react`,
    `eslint-plugin-react-hooks`, `@tanstack/eslint-plugin-query`) where their
    peer ranges allow, and say in the plan which ones could not be used.
  - `pnpm typecheck` (`pnpm -r typecheck`) picks up the frontend's
    `typecheck` script.
  - `pnpm test` runs Vitest and then the frontend's Jest suite;
    `pnpm test:unit` does the same (frontend tests use no external service);
    `pnpm test:frontend` runs Jest alone.
  - The frontend has no `build` script: native builds are dev builds or EAS.
- `frontend/README.md` holds the commands (like `backend/README.md`).

### Expo, not the blueprint's RN CLI — what changes

| Blueprint | Here |
| --- | --- |
| `react-native init`, committed `android/`, `ios/` | `create-expo-app`, `expo prebuild` (CNG); `app.config.ts` |
| `react-native-config`, `environments/*.env`, `ENVFILE=` | `EXPO_PUBLIC_*` variables, validated in `src/config/env` with Zod; per-environment non-secret values committed |
| Vite + `vite.config.mts` for web, `@remove-if-web` plugin | Expo's Metro web (`expo start --web`); platform files only |
| `babel-plugin-module-resolver` + `aliases.config.js` + sync test | `tsconfig.json` `paths` is the single source: Metro reads them natively, `jest.config.js` builds `moduleNameMapper` from them. No sync test needed. |
| `react-native-keychain` for the token | Not needed (see Auth). An adapter is added when something secret must be stored. |
| `index.js` + `AppRegistry` | Expo's `registerRootComponent` in `index.ts` |
| husky + lint-staged + commitlint | None (owner: no commitlint; the repo has no git hooks today) |

**Environments:** `development` and `production`. There is no stage backend.
`APP_ENV` selects the values and the app id suffix (`com.airremote.app.dev`
for development builds, so both can be installed side by side).
`EXPO_PUBLIC_API_URL` defaults to the local API for development. A physical
phone or the Android emulator reaches the host at another address than
`localhost` (`10.0.2.2` for the emulator, the LAN IP for a phone); the README
says how to override it.

### Directory structure, layers and naming

The blueprint's §2.2–§2.5 apply as written, inside `frontend/`, with these
adjustments:

- `src/ui/` holds the vendored kit (`src/ui/heroui/`), app-wide composites,
  the theme CSS, and `src/ui/index.ts`, which re-exports the public surface.
  App code imports `@ui` only. `@ui/*` is reachable only from `src/ui/` and
  `src/app/`.
- `@airremote/contracts` is pure (Zod and types, no platform code), so it is
  treated like `types`: any layer may import it, for types and for runtime
  schemas (a form validated with `loginRequestSchema`, say). `@app-types`
  holds only the app's own types (`ApiError`, navigation param lists, store
  shapes) and does not re-export contract types. Every API method validates
  its response with the contract schema. *(Builder's call, from the review.)*
- Styling is Tailwind classes through Uniwind (`className`), using the
  theme's tokens. A `<name>.styles.ts` file exists only for what classes
  can't express. The blueprint's "no hard-coded pixels or hex values" rule
  becomes "only theme tokens and Tailwind's scale; no arbitrary values".
- **Tests sit next to the file** (`<name>.test.ts(x)`), as the blueprint
  says, not in `__tests__/` folders: every component and hook already has its
  own folder. The root `CLAUDE.md` states this as the frontend's rule.
- Every architecture rule ESLint can check is enforced the way the blueprint
  shows (`eslint/layer-boundaries`, translated to flat config): the layer
  table, no cross-module imports, shared layers never import modules, no
  `../`. Also: only `src/ui/` imports the kit's dependencies (`uniwind`,
  `tailwind-variants`, the HeroUI peers) the way it does; only `src/api/`
  imports `axios`; only `src/adapters/` imports MMKV.

### Vendored HeroUI Native

- Copy `src/` of `heroui-inc/heroui-native` at tag `v1.0.11` (commit
  `1980fbb`) into `frontend/src/ui/heroui/`: components, primitives,
  helpers, providers, styles, optional. Not its tests, docs or example.
- Keep its `LICENSE` (Apache-2.0) and add `VENDOR.md`: upstream, version,
  commit, the exact changes made, and how to update.
- Its internal `from 'heroui-native'` imports (≈140) are rewritten to point
  at the vendored copy. Otherwise the code is unchanged in this change.
- It is excluded from our lint rules, Prettier and coverage, but it is type-
  checked (its own tsconfig is strict too).
- Its peer and direct dependencies are installed (Uniwind, Tailwind 4,
  `tailwind-variants`, `tailwind-merge`, Reanimated, Worklets, Gesture
  Handler, Screens, Safe Area Context, SVG, `@gorhom/bottom-sheet`,
  `expo-blur`, `@expo/vector-icons`, `expo-linear-gradient`, `expo-image`,
  `react-native-keyboard-controller`, as its source needs).
- `src/ui/index.ts` re-exports only what the app uses now (provider, Button,
  TextField and its parts, Card, Spinner, Toast, Dialog, Text, Surface) and
  grows as screens need more. Unused components are not bundled.
- **Toasts outside React:** `notifyApiError` runs in the query cache, outside
  any component. `@ui` provides a small imperative `toast` facade, connected
  to HeroUI's toast hook by a component mounted once inside the provider.
- HeroUI Native targets iOS and Android. Web goes through react-native-web
  and Uniwind's web support. **The plan starts with a web spike:** the
  vendored provider, Button, TextField and a toast rendered with
  `expo start --web`, before anything is built on the kit. Web rendering of
  the placeholder screens is a gate for this change, so fixes to the vendored
  copy that this needs are allowed, each recorded in `VENDOR.md`. If they go
  beyond the provider and those few components (a rewrite of the portal,
  bottom-sheet or animation layers, say), stop and bring it to the owner
  rather than forking the kit widely. *(Builder's call, from the review.)*

### API layer and the 401 refresh

The blueprint's Phase 5 stands, adapted:

- **`ApiError`** (the one rejection shape): `{ status?, code, message,
  details?, isNetworkError }`, where `code` is the server's `ErrorCode` or a
  client code (`NETWORK_ERROR`, `INVALID_RESPONSE`, `UNKNOWN_ERROR`).
  `toApiError` reads `errorResponseSchema`.
- **`httpClient`** methods take the response schema and resolve with the
  parsed body: `httpClient.get(url, schema, config)`. A body that fails the
  schema rejects with `INVALID_RESPONSE`, so a backend/frontend contract
  drift is a visible error, not a crash later. A 204 takes no schema.
- **Request interceptor:** adds `Authorization: Bearer <token>` unless the
  request is `skipAuth`.
- **Response interceptor (the refresh):** for a 401 on a request that carried
  a token and has not been retried yet:
  1. Call `refreshAccessToken()`. Concurrent 401s share one in-flight
     refresh: the http client holds a single pending promise.
  2. On success, retry the original request once with the new token.
  3. On failure (`INVALID_REFRESH_TOKEN`, or anything else), call
     `onSessionExpired()` and reject with the original request's `ApiError`.
  A 401 on a `skipAuth` request (login, refresh) never triggers a refresh.
- The http client never imports stores or `authApi`. `bootstrap.ts` injects
  `getAccessToken`, `refreshAccessToken` (calls `authApi.refresh()` and stores
  the new token) and `onSessionExpired` (signs out locally and clears the
  query cache), as the blueprint's `configureHttpClient` does.
- **Cookies:** on iOS and Android the native networking stack keeps and sends
  the refresh cookie. On web, the `/auth` calls set `withCredentials`.
- `authApi`: `login` (`skipAuth`), `refresh` (`skipAuth`), `logout`, typed
  with `loginRequestSchema` and `accessTokenResponseSchema`.

No proactive refresh before expiry: reactive is what V1 did and enough.

### Backend: CORS

The web app runs on another origin than the API (`localhost:8081` and
`localhost:3000` in development), so the browser needs CORS with credentials
for the refresh cookie and the JSON calls.

- `@fastify/cors` registered in `app.ts`, with `credentials: true` and the
  allowed origins from a new `CORS_ORIGINS` variable (comma-separated
  origins, validated in `src/config/env.ts`, empty means CORS off).
  `.env.example` sets it to the Expo web dev server's origin.
- It is not a wildcard: with credentials, only listed origins are allowed.
- Tested like the rest of the backend: unit tests for the env parsing, and an
  e2e test that a preflight and a credentialed request from an allowed origin
  get the CORS headers, and one from another origin does not.
- `backend/README.md` documents the variable.

### Auth state

- `authStore` (Zustand, not persisted) holds `accessToken` and `status`:
  `hydrating` → `authenticated` | `anonymous` | `hydration-failed`.
- **Startup:** `authStore.hydrate()` calls refresh. A token means
  `authenticated`; `INVALID_REFRESH_TOKEN`/401 means `anonymous`; a network
  error or 5xx means `hydration-failed`, and the root navigator shows a
  "couldn't connect, retry" screen.
- **Login:** `useLogin()` runs the login mutation and stores the token.
  There is no "stay logged in" choice: the refresh cookie is what keeps the
  session, as in V1.
- **Logout:** `useLogout()` calls `POST /auth/logout` (clears the cookie),
  then signs out locally and clears the query cache, also when the request
  fails (logged with `logError`).
- V2 has no "current user" endpoint, so `useAuth()` derives `isLoggedIn` from
  the auth status alone. No user details are shown in this change.

### State, queries, hooks, navigation, i18n, app root

The blueprint's Phases 6–10 apply as written, except where this document
says otherwise: the query client factory with injected error presentation
and the typed `Register` (`defaultError: ApiError`), key factories and
`queryOptions`, mutation hooks owning cache effects, the online/focus
managers wired to NetInfo/AppState on native, `useRefreshOnFocus`, the store
facade pattern with `INITIAL_*_STATE` and `reset()`, scoped stores via
context, `useDebouncedValue`, typed navigation with `navigationRef`, typed
i18n keys, the persisted `preferencesStore` (language) with
`useSyncLanguage`, and `bootstrap()` before the first render.

- **Error toasts** translate by error code (`errors.<CODE>` in the
  `messages` namespace), then the query's `meta.errorMessage`, then a generic
  message. The server's `message` is for developers and is not shown.
- **Languages:** English only (default and fallback).
- **Screens in this change:** placeholders that prove the plumbing, using
  `@ui`:
  - a Login screen with a minimal working form (email, password, submit;
    react-hook-form validated with `loginRequestSchema`), unstyled beyond the
    kit's defaults. The next change replaces its look with V1's.
  - a Home screen saying the user is signed in, with a Sign out button.
  - the loading and "couldn't connect" screens.
  The root navigator gates on auth status.
- The theme follows the system's light/dark scheme through HeroUI's theme
  for now. V1's colours come with the next change.

### Testing

Jest with `jest-expo`, `@testing-library/react-native` (its `renderHook` and
`userEvent`), `babel-jest` only. The blueprint's Phase 11 applies: global
mocks in `jest.setup.ts`, `createTestQueryClient` / `createQueryWrapper` /
`renderWithProviders`, mock at the API boundary (`@api/http-client` or the
domain API), real query clients and stores. Required coverage:

- `toApiError` and the http client, including the refresh: a 401 refreshes
  and retries; concurrent 401s refresh once; a failed refresh calls
  `onSessionExpired` and rejects; `skipAuth` requests never refresh; a body
  failing its schema rejects with `INVALID_RESPONSE`. The client is tested
  against a mocked axios adapter, not a mocked axios module.
- `authApi`, the auth queries/mutations, `authStore` (hydrate outcomes,
  sign in, sign out), `preferencesStore`, `useAuth`, `useLogin`, `useLogout`,
  `useDebouncedValue`, `useRefreshOnFocus`, the utils, the env parsing, and
  the Login screen (submits, shows validation errors).

### Scaffolding

`frontend/scripts/create-new.mjs`, Node built-ins only, as blueprint Phase 12
describes, with the templates matching this design (Tailwind classes, tests
next to the file, contract-validated API methods). `pnpm create-new <kind>
<name>` from `frontend/`. Kinds: `component`, `screen`, `hook`, `store`,
`domain`, `helper`, `module`. It is checked by generating each kind once and
running lint, typecheck and tests on the result.

### Documentation and skills

- **Root `CLAUDE.md`:** a "Frontend conventions" section, as short as the
  backend and firmware ones: the stack, the layers and the rules ESLint
  enforces, state ownership, `@ui` only, tests next to the file, where the
  details are.
- **`frontend/ARCHITECTURE.md`:** the contract for humans and agents: the
  tree, layer table and import rules, state ownership, naming, the API layer
  and refresh flow, and the blueprint's pitfalls that apply. The blueprint's
  RxJS translation table is left out: there is no RxJS code to port.
- **Skills in `.claude/skills/`**, each a procedure with a checklist that
  points at `ARCHITECTURE.md` for the why rather than repeating it:
  - `frontend-feature` — a new feature end to end (blueprint §15.1): contract
    types, API, queries, module, i18n, screens, navigator, tests.
  - `frontend-api` — a backend domain's API object, query keys/options and
    mutation hooks, validated with the contracts (§15.7, Phases 5–6).
  - `frontend-ui` — components, screens and navigators with `@ui` and
    Tailwind classes; adding to or changing the vendored kit and its
    `VENDOR.md` (§15.2–15.4).
  - `frontend-state` — choosing where state lives; global, module and scoped
    stores; hooks that compose queries and stores; contexts (§2.4, Phase 7–8,
    §15.5–15.6, §15.11).
  - `frontend-logic` — helpers and constants (§15.8–15.9).
  - `frontend-platform` — platform files and adapters, web differences
    (§15.10).
  - `frontend-i18n` — namespaces, typed keys, adding a language.
  - `frontend-testing` — what to test per layer and how (Phase 11).
  - `frontend-dev` — running the app: env, dev server, dev builds on the
    Android emulator or a phone, web, EAS for iOS, common failures.
  Each skill's description says when to use it, so it fires when relevant.
- `REACT_NATIVE_BLUEPRINT.md` is not committed: what applies lives in
  `ARCHITECTURE.md` and the skills.

## Verification

- `pnpm lint`, `pnpm typecheck`, `pnpm test` pass at the root.
- A deliberate layer violation (`@api/...` from `src/helpers/`), a
  cross-module import and a `../` import each fail lint, then are removed.
- `create-new` output for every kind is lint-, type- and test-clean, then
  deleted.
- `expo-doctor` passes. `expo prebuild` generates `android/` and `ios/`
  cleanly (not committed).
- Web, against `pnpm dev`, in a real browser with a clean console and
  network: the app starts on Login (the startup refresh answers 401), shows
  validation messages, shows the error toast for wrong credentials, signs in
  to Home, survives a reload (the cookie refreshes the session), and signs
  out.
- The backend's CORS tests pass as part of `pnpm test`.
- Android and iOS boot checks need the Android SDK (not installed here: Java
  is 25, Android builds want 17) or EAS. They are listed in
  `frontend/README.md` as manual steps for the owner: install, sign in, see
  Home, background/foreground, airplane mode, wait 10 minutes and use the
  app (refresh is invisible), sign out.

## Risks and open points

- **Web cookies across origins.** `SameSite=Strict` ignores ports, so the
  refresh cookie works between `localhost:8081` and `localhost:3000`. In
  production, web and API must be on the same site (e.g. `app.` and `api.`
  of one domain), or the cookie's `SameSite` must change. That is decided
  when web is deployed.
- **Native cookie persistence.** The refresh cookie must survive an app
  restart. iOS persists cookies with an expiry, and Android's React Native
  networking stores them in the system `CookieManager`, but this is
  unverified on this app. If it fails on a device, the fallback is the
  backend also returning the refresh token in the body for native clients,
  kept in `expo-secure-store`. That is a backend and contract change, decided
  when it happens.
- **Vendored kit on web** may need fixes per component (above).
- **ESLint 10 and React Native plugins:** if a plugin doesn't support ESLint
  10, the plan says what replaces it. Lowering the repo's ESLint version is
  not an option without asking.
